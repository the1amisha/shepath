## 7. Failure recovery and offline contingency

Operational presenter rule: spend at most roughly **20–30 seconds** explaining an unexpected wait before switching to the rehearsed alternative. This is a presentation budget, not a change to the application timeouts.

| Failure | Existing behavior / limit | Recovery during demo |
|---|---|---|
| Routing network/provider/backend error | Client has 60 s request signal; backend upstream timeout is 15 s per HTTP operation, with potentially several geocoding/directions operations. Error text can mention CORS/configuration; no automatic mock fallback. Leaving logically invalidates the request but does not abort transport. | One deliberate Try again after restoring the known service; otherwise open saved comparison and explain it is historical. Do not repeatedly submit or accept a stale result. |
| Pending route → saved → return | Explicit interruption status and Retry route/Edit journey; no selected route until a fresh result | Use the visible recovery control. Old request completion must not populate the new view. |
| Evidence busy | One job per worker; client serializes and retries explicit busy at most twice, with 5–15 s backoff | Keep comparing routes or use saved view. Do not open competing tabs to speed it up. |
| Evidence timeout | Backend response deadline 60 s; browser request deadline 75 s. Queue wait is additional. Timed-out native work retains its slot until it finishes | Continue without evidence or use saved comparison. If persistently stuck, restart only the owned worker off-stage, then rerun smoke checks. No guarantee that a browser abort frees server capacity. |
| Dataset/dependency unavailable | Explicit error; initialization failure latched until restart | Restore the known verified installation and restart off-stage. Never replace evidence with empty data, edit pins or regenerate an extraction on stage. |
| Coverage unavailable | Valid HTTP result with no route context; whole geometry/buffer outside pilot | Show the honest extent message. Explain the limitation or use the rehearsed covered journey; do not display zero facilities or saved metrics as substitutes. |
| Map import/setup/tile failure | Separate status; route text/selection/evidence remain usable; two manual map retries per mounted view | Use route cards and next actions. Retry map once after connectivity returns. Cached failed imports can require a full reload, which also resets the journey. | Saved comparison failure | 30 s abort signal; error and manual Try again; no embedded runtime fixture fallback | Check backend/base URL and verified bundle; retry once. If unavailable, use prepared historical documentation or recording, explicitly labeled. |
| Occupied port / wrong origin | Startup refuses bind; unsupported origin can fail CORS | Identify/reuse the known process or stop your own old server. Frontend 8081 is allowed if chosen explicitly; backend URL must match. Do not let a silent port change drive the demo. |
| Full reload/crash | React journey state resets | Restart the rehearsed sequence, or switch to prepared material. Refresh is not route persistence. |

### Offline layers

1. **WAN unavailable, localhost healthy:** the saved comparison can still load from the local backend and verified files; dynamic evidence can analyze already-held coordinates. New live geocoding/directions cannot be assumed to work, and tiles/fonts may be absent. Avoid reloading a useful already-loaded live journey unnecessarily. No WAN-disconnection rehearsal was performed here.
2. **Local backend unavailable:** the currently loaded UI can demonstrate existing state, but saved comparison is not an offline cache. A separately rehearsed mock-mode start (`VITE_ROUTING_PROVIDER=mock`, restart frontend) can illustrate the five-step interface with clearly labeled fixed geometry and no dynamic evidence. Do not silently switch modes or present mock values as live observations.
3. **Application unavailable:** prepare redacted screenshots or a short local recording during a successful rehearsal, annotated with date, mode, journey and historical snapshot. Keep copies of the tracked `ROUTE_COMPARISON_REPORT.md`, `DYNAMIC_ROUTE_EVIDENCE_REPORT.md` and this audit accessible locally. Explain these are recorded/historical results. This audit did not create or certify a recording.

No service worker, offline tile package or durable journey cache was established. “Saved” refers to persisted server artifacts, not an offline-capable browser app. Do not download replacement datasets or add a paid provider for this demo.

## 9. Remaining limitations and final presentation decision

- Live provider availability, quota, geocoding correctness and returned alternatives vary; this successful HTTP run does not guarantee the next one.
- Current loaded server provenance and a cold start were not established; clean installation and portable dependency resolution remain unverified.
- Browser hydration, real tiles, rendered layout, keyboard/AT output, contrast and physical devices remain manual acceptance work. HTTP and DOM tests cannot substitute for them.
- Geographic evidence is historical, bounded and incomplete. Mapped proximity, tags, zero counts and unknown values do not establish personal safety, current operation, street lighting, sidewalk continuity, accessibility or actual conditions on the walked street. Duplicate establishments and category overlaps remain explicitly uncertain.
- Saved comparison uses a different fixed journey/snapshot identity from arbitrary live routes. Its preference groups are not safety rankings and do not affect the five-step preference preview.
- Evidence work is sequential with one job per worker; native work can outlive HTTP cancellation/deadlines. Queue time, full JSON transfer and transient parsing memory remain costs. No load/total-memory certification was performed.
- No dedicated evidence retry, tile-stall deadline, durable offline mode, browser-step history or persistent journey state exists. Map selection recreates Leaflet and resets its view.
- The frontend lint gate fails; root/setup documentation and environment examples need maintenance. Git secret-ignore/tracked-file checks were performed, but no comprehensive historical secret/security audit or dependency vulnerability scan was conducted.
- No application fixes, snapshot changes, dependency updates, commits or pushes were made in Phase 7A.

**Decision:** proceed to a controlled desktop rehearsal. Present once startup/process ownership, the five-step browser journey, recovery paths and local fallback are confirmed. Address any reproduced blocking interaction immediately; documentation/configuration consistency and small focus/source-readability improvements are the minimal 7B work. Broad mobile polish, bundle cleanup, map refactoring and persistence can safely wait for a rehearsed desktop-only presentation, with their limitations stated.
